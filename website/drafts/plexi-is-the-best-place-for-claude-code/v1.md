Claude Code does not need another chat wrapper.

It needs a better place to work.

The default place to run Claude Code is a terminal tab. That works because Claude Code is a CLI tool, and CLIs belong in terminals.

But once you use it seriously, the tab starts to look thin.

Claude is editing files, asking for permission, running commands, waiting on tests, reading output, getting blocked, resuming, stopping, and starting over. Meanwhile the terminal around it mostly knows one thing: bytes went in, bytes came out.

Plexi changes the layer around the agent.

## The terminal is not enough state

Claude Code has its own internal session. Your terminal has scrollback. Your repo has files. Your shell has environment variables. Your notes live somewhere else. Your dev server is in another tab. Your tests are in another one. Your GitHub issue is in a browser.

That is too many places for one agent loop.

When the work is simple, it is fine.

When the work is real, you start needing operations:

- Is Claude working, blocked, or idle?
- Which pane is it in?
- What was the last output from the test runner?
- Which context does this session belong to?
- Did it request permission?
- Did it stop cleanly?
- Where should I leave a note without derailing the session?
- Which API key does this workspace use?

Plexi answers those questions at the host level.

## Claude Code hooks become visible

Plexi has a Claude Code hook integration:

```sh
plexi agent hook install --claude-code
```

That patches Claude Code settings with hook registrations for lifecycle events, including tool use, permission requests, session start, user prompt submit, stop, stop failure, and session end.

Those hooks report agent state back to Plexi:

```sh
plexi agent report --state working --agent claude-code
```

Then Plexi can show agent status across panes:

```sh
plexi agent status
```

This is the first big difference.

In a normal terminal, Claude is "some process in some tab."

In Plexi, Claude can become a visible actor in the workspace.

Working. Blocked. Idle. In this pane. In this context. Attached to this session.

That is not decoration. It is operations.

## Panes give agents handles

Plexi panes have IDs.

You can list them:

```sh
plexi pane list
```

You can name them:

```sh
plexi pane name "api server"
```

You can capture output:

```sh
plexi pane capture --lines 80
```

You can send input:

```sh
plexi pane command 42 "cargo test --bin plexi" --enter
```

That means a human or agent can treat the workspace as structured state.

The dev server is not "that tab on the left."

It is pane 12, named `dev server`, in the current context.

The test runner is not "the tab I think is third from the right."

It is pane 18, and Plexi can capture its last output.

Claude Code is strongest when it has cheap, accurate feedback. Plexi gives it a better substrate for feedback than raw terminal tabs.

## Contexts keep work from bleeding together

Claude sessions get messy when everything shares one mental workspace.

One pane is debugging a UI bug. One is writing a feature. One is running a long server process. Another is a half-finished investigation you should not lose.

Plexi has contexts and subcontexts.

You can open a new context for a project, push a pane into a subcontext, describe the active context, zoom into a subcontext, and list what is open.

For agent work, that matters because context is not just a directory. It is intent.

`/Users/ian/project` tells an agent where files live.

"PR validation lane for issue 2162" tells an agent why the panes exist.

Plexi can carry both.

## Secrets stop being agent bait

AI workflows are full of API keys.

The lazy setup is to export keys in your shell. That works until it works everywhere.

Plexi has workspace-scoped secrets stored through the system keychain. You can set a key inside a project, set a global fallback, list keys without showing values, and delete them when they are no longer needed.

Apps request secrets through `secrets.get`. Workspace secret injection is being shaped around allowlisted environment names like `OPENAI_API_KEY`, `OPENROUTER_API_KEY`, and `ANTHROPIC_API_KEY`.

That is the right default for agent-heavy work:

The agent gets the credentials this workspace is supposed to use.

Not every credential you have ever pasted into a shell file.

## Notes stay in the work

Claude Code sessions create side thoughts constantly.

"File an issue for this."

"This test harness is brittle."

"Try a second implementation later."

"This is a product idea, not part of the current fix."

In a normal terminal setup, those thoughts become distractions. You either chase them, lose them, or paste them into a random app.

Plexi has Quick Note and notes/backlog flows. Capture the thought, route it, keep moving.

This is especially useful with agents because the human job is often judgment, not typing. You need a low-friction way to leave breadcrumbs without yanking the agent out of its lane.

## Notifications make long-running work humane

An agent should not require babysitting.

Plexi processes and apps can send notifications to the host. A test run can tell you it failed. A script can ask for a choice. A background task can surface when it needs attention.

That pairs naturally with Claude Code.

Claude can run in one pane while another pane runs tests, logs, a local server, or a generated app. When something needs a human, Plexi can put it in the notification queue instead of relying on you to notice a scrollback change.

This is how agent work should feel: not watching a terminal, but supervising a workspace.

## Apps beside the agent

Plexi can run app panes beside terminal panes.

That means Claude can work next to:

- a live Logs app
- a GitHub Issues app
- a Todo app scoped to the workspace
- a Permissions app
- a generated tool built for the task
- an MCP server wrapped into a Plexi pane
- a CLI tool wrapped with a visual UI

This is a different direction from web-based agent IDEs.

Plexi keeps the terminal as the base layer, then adds app surfaces where they make the work clearer.

Claude still gets the shell.

The human gets the workspace.

## The real claim

Plexi is not better because Claude Code cannot run elsewhere.

Claude Code runs fine in any terminal.

Plexi is better because serious Claude Code work is no longer just "run Claude Code."

It is:

- run Claude Code
- keep supporting panes alive
- name the panes
- capture outputs
- scope secrets
- track agent state
- keep notes
- route notifications
- separate contexts
- inspect app state
- eventually let agents subscribe to app events and call app tools through the permission broker

That is an operating layer.

Most terminals give Claude a box.

Plexi gives Claude a workplace.

## Before and after

Before Plexi:

Claude Code runs in a tab. You manually remember what it is doing. You manually check logs. You manually find the test pane. You manually paste notes somewhere else. Your secrets come from shell config. The terminal cannot tell you which agents are blocked.

After Plexi:

Claude Code runs in a named pane, inside a context, with lifecycle hooks reporting state to the host. The workspace has panes the agent can address, output it can capture, notes you can route, notifications that surface attention, and secrets scoped to the project.

That is why Plexi is the best place to run Claude Code.

Not because it hides the terminal.

Because it finally gives the terminal the missing agent layer.
