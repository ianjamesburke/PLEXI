There is a moment in every AI coding session where the terminal stops feeling powerful and starts feeling like a junk drawer.

You know the moment.

One tab is running the dev server. One tab has Claude Code halfway through a plan. One tab is sitting in the wrong directory. One tab has the error you needed, but you lost it behind three other tabs. One tab is asking for permission. One tab is a command you are afraid to interrupt because you cannot remember if it is doing anything.

Nothing is technically broken.

That is the frustrating part.

The terminal is doing exactly what it promised. It gives you a prompt. It runs a process. It prints text.

But now the work is bigger than that.

The work is not "run a command." The work is: keep the server alive, watch the logs, let Claude edit, run tests, approve tool calls, remember a follow-up idea, keep the right API key in the right project, maybe open a tiny UI for the thing you are inspecting, then come back two hours later and understand what is still alive.

A normal terminal turns all of that into tabs and scrollback.

Plexi starts from a different assumption:

What if the terminal is not the app?

What if the terminal is one piece of the workspace?

## The first problem is not layout. It is memory.

Most terminal upgrades start with layout.

Split panes. Tabs. Better fonts. Better colors. Command palettes. Nice.

But the pain is not that the rectangles are ugly.

The pain is that the rectangles forget what they are.

If you have six tabs open, the computer does not know which one is the server, which one is tests, which one is Claude, which one is safe to close, and which one contains the one stack trace you still need.

You know, until you do not.

Plexi gives panes identity.

You can split them. Move through them. Rename them. List them. Capture their output. Send commands into them. Focus them by ID. A pane can be "api server" instead of "tab 4, I think."

That sounds boring on paper.

It is not boring when an agent is involved.

An agent cannot reliably work with "the pane on the left with the logs." It needs handles. It needs to ask, "what panes exist?" and "what did pane 17 just print?"

Plexi makes terminal work addressable.

That is the first step out of the junk drawer.

## Then the second problem shows up: projects bleed into each other.

At first, one workspace is enough.

Then you open another repo.

Then you are debugging a branch in the first repo while a server from the second repo is still running. Then Claude is in a pane you forgot was attached to the old context. Then an API key works in one terminal but not another. Then a note says "fix this later" and you cannot remember which "this" it meant.

This is where normal terminals give up and make you be the operating system.

Plexi has contexts.

A context is a project-shaped container. It has a root, panes, app instances, descriptions, secrets, and subcontexts. You can zoom into one. You can push a pane into a child context. You can separate a tangent without losing it.

That matters because real work branches.

You start on the bug. You find a test problem. You notice a product idea. You see a cleanup you should not do right now.

In a normal terminal, tangents become either distraction or amnesia.

In Plexi, they can become subcontexts.

You do not have to keep the whole tree in your head.

## Then you hit the API key problem.

Every AI workflow eventually becomes credential management.

OpenAI key. OpenRouter key. Anthropic key. GitHub token. Stripe key. Database URL. Maybe a local model. Maybe a staging key. Maybe a client key that absolutely should not leak into the wrong project.

The usual answer is shell config.

Paste it into `.zshrc`. Or `.env`. Or some private include file. Or export it once and forget which terminal has it.

This works until it does exactly what you told it to do: make the secret ambient.

Plexi has a secret store.

You can set a key through the CLI. You can scope it to a workspace or make it global. Values live in the system keychain. Apps request secret access through a declared capability.

The important part is not the command.

The important part is the shape:

"This workspace is allowed to know this credential."

That is a better default than "every shell I open might have whatever I pasted six months ago."

AI tools are going to touch more of your machine, not less. Secrets cannot stay a shell trivia question.

## Then apps start wanting permissions.

A normal terminal has a blunt trust model.

If you run it, it runs as you.

That is simple. It is also a bad fit for an environment full of small apps and agents.

Plexi does not pretend v1 apps are sandboxed. Native Python apps are still native processes. You should treat them like shell scripts.

But Plexi does introduce a protocol boundary.

Plexi apps declare capabilities. If an app wants to use host APIs for files, network, secrets, AI, panes, audio, or timers, it asks through PGAP. The host can prompt. The decision can be recorded. The action can be logged.

That is the part that matters for the future.

The future is not "trust every tiny AI-generated tool with your whole machine."

The future is "this actor wants this action on this target in this scope."

Plexi is building toward that.

## Then you realize notes are part of terminal work.

Nobody talks about the cost of switching to a notes app because it sounds small.

It is not small.

You are in the middle of a debugging session. Claude just surfaced a weird edge case. You should file an issue. You should write down the command that worked. You should remember that this test is flaky. You should not stop the current thread to do any of that.

So you do what everyone does.

You trust future-you.

Future-you is busy.

Plexi has Quick Note because capture has to be cheaper than forgetting. One shortcut, write the thought, route it, keep moving. The note can go to a backlog, a pane command, or another configured destination. Scratchpad notes are local files.

This is one of those features that looks small until it changes the texture of the day.

The terminal becomes a place where thoughts can land without becoming interruptions.

## Then waiting becomes the enemy.

Modern work is full of waiting.

Tests. Builds. Deploys. Agents. Transcodes. Scrapers. Long-running scripts. Anything with a spinner and a chance of failure.

Most terminal workflows make you poll them with your eyeballs.

Plexi has notifications.

A process can tell the host it is done. It can ask for a choice. It can scope the notification to a window, context, or the whole app. Apps can notify too.

That turns a terminal command into something more like a participant.

It can leave the pane, do its work, and come back when it needs you.

That is what computers are supposed to do.

## Then the terminal needs a UI, but not a whole app.

Some things should not be plain text.

Logs are easier when they are filtered and colored. CSVs are easier as tables. Permissions are easier in a focused surface. GitHub issues are easier beside the repo. A todo list is easier when it is not a markdown file you forgot to open.

Plexi can run app panes next to terminal panes.

These are not random webviews. They are PGAP apps. They declare capabilities. They render into the same workspace. They can use the same host systems for secrets, notifications, logs, AI, and input.

This is the part where Plexi stops looking like a terminal emulator and starts looking like a personal computing environment.

The shell is still there.

It is just no longer alone.

## Then Claude Code changes the stakes.

Claude Code works in any terminal.

That is not the point.

The point is that Claude Code turns your terminal into an agent workplace. Once that happens, the terminal needs to know more.

Is Claude working?

Is it blocked?

Did it request permission?

Which pane is it in?

Which project is it attached to?

What else is running around it?

Plexi has Claude Code hook integration. It can install hooks for lifecycle events like tool use, permission requests, session start, prompt submit, stop, failure, and session end. Those hooks report agent state back into Plexi.

So instead of "Claude is somewhere in one of my tabs," you get "Claude is working in this pane, in this context."

That is the beginning of the agent layer.

## The before and after

Before Plexi, I was not using a bad terminal.

I was using a terminal for a job that had outgrown terminals.

I needed panes, but also names.

I needed tabs, but also context.

I needed environment variables, but also scoped secrets.

I needed scripts, but also notifications.

I needed apps, but inside the workspace.

I needed Claude Code, but with visibility into what it was doing.

That is the before and after.

Before Plexi, the workflow lived in my head.

After Plexi, the workflow has somewhere to live.

That is why Plexi exists.

Not to make the terminal prettier.

To give the terminal a memory.
