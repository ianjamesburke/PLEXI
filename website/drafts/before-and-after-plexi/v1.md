Most terminals are memoryless rectangles.

They are good at one thing: giving you a prompt. That was enough when the job was typing commands by hand. It is not enough when your terminal is where your servers run, your agents work, your API keys live, your notes get captured, your app tools launch, your logs stream, and your entire project state unfolds.

That is the gap Plexi is built for.

Plexi is not trying to be a prettier terminal. It is trying to become the working environment around the terminal. A place where panes have names, projects have context, secrets have scope, apps declare permissions, agents report state, notes get captured, notifications come back to the surface, and everything still feels like a terminal when you need it to.

Before Plexi, I had tabs.

After Plexi, I have a workspace.

## Before

You open your usual terminal.

You start a dev server in one tab. You open another tab for git. Another for tests. Another for Claude Code. Another for logs. Then one more because you need to check an API response. Then one more because you forgot which directory the old one was in.

Now the whole day is tab archaeology.

One tab says `npm run dev`. One tab says `zsh`. One tab is halfway through a stack trace. One tab is Claude asking for permission. One tab has the command you needed ten minutes ago, but the prompt scrolled off the screen.

The terminal did not do anything wrong. It gave you a shell. That is the contract.

But your work is no longer one shell.

Your work is a live arrangement of processes, state, context, credentials, agents, logs, and decisions. A normal terminal treats all of that as text.

Plexi treats it as an environment.

## After

In Plexi, the first difference is spatial.

You split panes with the keyboard. You move through them with direction keys. You name them. You can ask Plexi what panes are open. You can focus one by ID. You can capture the last 50 lines from a pane without clicking around. You can send a command into another pane like it came from the keyboard.

That sounds small until you have multiple agents working.

An agent does not want vibes. It wants handles.

It wants to know:

- which pane is the dev server
- which pane is the test runner
- which pane is Claude
- what the last output said
- where the current project root is
- what context it is operating inside

Plexi gives terminal work names, IDs, context, and structure. That is the difference between "a pile of tabs" and "a workspace an agent can operate."

## Secrets stop being shell trivia

Most people learn API keys the worst way possible.

Some tutorial tells them to paste a key into `.zshrc`. Another tool wants `.env`. Another wants a config file. Then six months later they have no idea which key is active, which project it belongs to, or why one terminal can see it and another cannot.

Plexi has a built-in secret store.

You can set a secret once:

```sh
plexi secret set OPENAI_API_KEY
```

You can scope it to a workspace or make it global. Values are stored through the system keychain. Apps request secrets through a host-brokered capability. A secret for one project does not silently become a secret for every project.

That matters because AI work is credential-heavy. OpenRouter, OpenAI, Anthropic, Stripe, GitHub, NVIDIA, database URLs - the more capable your workspace gets, the more dangerous sloppy secret handling becomes.

A normal terminal inherits whatever your shell gives it.

Plexi can make credentials part of the workspace contract.

## Permissions become visible

In a normal terminal, everything you run is just a process with your user permissions. If it can read your home directory, it can read your home directory. If it can open a network socket, it can open a network socket.

Plexi is honest about its current security model: native Python apps are not sandboxed yet. You should treat them like shell scripts, not browser tabs.

But Plexi still gives you something a normal terminal does not: a protocol boundary.

Plexi apps declare capabilities in a manifest. If an app wants to call host APIs for secrets, AI, files, network, panes, audio, or timers, that request goes through PGAP, Plexi's app protocol. The host can prompt. The decision is stored. The action can be logged.

That is not the same thing as a WASM sandbox, and Plexi does not pretend it is.

But it is the right shape.

The future of AI software needs permissions that humans can understand and agents can reason about. "This app wants `secrets.get` in this workspace" is a better primitive than "run this random process and hope."

## Apps live inside the terminal environment

Plexi has terminal panes, but it also has app panes.

An app pane is not a web tab floating beside your terminal. It is a process that speaks PGAP. It can render UI, receive input, send notifications, request secrets, query AI, read files, write files, and report status through the host.

The core apps already show the shape:

- Backlog for browsing captured notes
- Logs for live host logs
- Permissions for managing app grants
- Todo for workspace tasks
- GitHub Issues for the repo in front of you
- CSV Viewer for inspecting local data
- Calculator, Wikipedia, Stats, games, and agent examples

The point is not that Plexi ships a calculator.

The point is that Plexi can host tiny purpose-built apps next to the shell that needs them. If you need an app for one project, you can scaffold it, run it in a pane, and keep it inside that workspace.

In a normal terminal, the next step after "I need a UI for this" is usually "open a browser" or "build a whole app."

In Plexi, the next step is:

```sh
plexi app init my-tool
```

The app opens beside your code.

## Notes are part of the flow

The dumbest productivity failure is losing the thought that occurred while you were doing the work.

In a normal terminal, you either break flow to open Notes, paste something into Slack, add a TODO in a file you will never see again, or trust yourself to remember.

Plexi gives you Quick Note.

One shortcut opens a capture overlay. Write the thing. Send it to the backlog, a pane command, or a configured destination. Keep working.

There is also a notes command for browsing scratchpad notes from the terminal. Notes are files on disk. The backlog is not a cloud service. It is not another app subscription. It is part of the environment.

That changes how you work because capture becomes cheap enough to use.

## Notifications come back to the right place

Long-running work should not require staring.

In Plexi, a process can send a notification to the host:

```sh
plexi notify --title "Deploy ready" --body "Review before promoting."
```

Notifications can be global, scoped to a context, or scoped to a window. They can include choices. Apps can send them too. High-priority ones can interrupt; lower-priority ones can wait in the queue.

That means a terminal command can ask a human a question without becoming a bespoke UI.

This is one of the places Plexi starts to feel less like a terminal and more like a small operating system for work. The terminal launches the work. Plexi routes the attention.

## Contexts replace mental bookkeeping

Plexi has contexts.

A context is a project or workspace scope. It can have a root directory, description, panes, app instances, secrets, and subcontexts. You can zoom into a subcontext, push a pane into a new subcontext, list open contexts, and keep work separated without pretending your brain is a tab manager.

This matters because modern work is nested.

You are not just "in the repo." You are in:

- the bug
- the reproduction
- the branch
- the PR
- the logs
- the agent lane
- the follow-up idea you should not chase yet

Most terminals flatten all of that into tabs.

Plexi gives it a structure.

## The Claude Code story

Claude Code is already good. Plexi makes it easier to live with.

Plexi can install Claude Code hooks that report lifecycle events back into the host: tool use, permission requests, session starts, prompt submits, stops, failures, and session end. Plexi can show agent state across panes: working, blocked, idle.

That is the beginning of an agent operating layer.

A normal terminal can run Claude Code.

Plexi can surround Claude Code with panes, state, context, secrets, notes, logs, and notifications that the host understands.

That is the real comparison. Not "does Plexi have a prompt?" Every terminal has a prompt.

The question is: what does the prompt live inside?

## Before and after

Before Plexi:

You open tabs. You name nothing. You paste secrets into shell config. You lose notes. You forget which pane is doing what. Claude runs in a rectangle with no durable relationship to the rest of the workspace. Apps live elsewhere. Logs live elsewhere. Notifications live elsewhere. Your computer has the information, but the workflow is still in your head.

After Plexi:

The workspace has shape. Panes can be named, queried, captured, focused, and controlled. Secrets can belong to a project. Apps can ask for capabilities. Notes get captured into files. Notifications route back to the UI. Agents can report state. Contexts and subcontexts keep separate pieces of work separate.

It is still a terminal when you need a terminal.

It is more than a terminal when the work becomes more than a command.

## Why use Plexi over another terminal?

Use another terminal if all you need is a prompt.

Use Plexi if your terminal has become the place where your work actually lives.

Use Plexi if you run agents and want to know what they are doing.

Use Plexi if you are tired of API keys leaking into random shell startup files.

Use Plexi if you want local apps that sit beside your shell instead of another SaaS tab.

Use Plexi if your notes, logs, commands, contexts, and AI sessions should belong to the same environment.

The terminal won because text is composable.

Plexi exists because text is not enough anymore.

The next terminal needs memory. It needs permissions. It needs apps. It needs context. It needs to be scriptable by agents and still owned by the person using it.

That is Plexi.
