## Channel-Agnostic CLI Rule

Every CLI command and feature must work identically on alpha, beta, main, and PR builds. The release channel is an implementation detail. See `scripts/RELEASE_CHANNELS.md` for the channel table and shim behavior.

**Path rules:** Never hardcode a profile directory path — always use `config_dir()`. Never hardcode `.plexi/` as a workspace dir — always use `workspace_channel_dir()` or `workspace_config_path()`.

**Socket rule:** An explicit `--socket` wins, followed by binary identity: a channel-suffixed binary resolves its own profile endpoint and ignores an inherited `PLEXI_SOCKET` (logged). Only the bare `plexi` binary adopts ambient `PLEXI_SOCKET`, and with none it has no command socket. Self-identity vars (`PLEXI_PANE_ID`, `PLEXI_CONTEXT_*`, `PLEXI_RUNNING`) feed defaults only, never routing. Route new command dispatch through `resolve_command_socket()`. On Windows the endpoint is the stable `\\.\pipe\plexi-<channel>` named pipe, never a filename-derived `.exe` suffix.

**Environment classification (`self-identity` vs `target-routing`):**

| Class | Inputs | Role | Precedence / Resolution Contract |
|---|---|---|---|
| `self-identity` | `PLEXI_PANE_ID`, `PLEXI_CONTEXT_ID`, `PLEXI_CONTEXT_ROOT`, `PLEXI_RUNNING` | Read-only facts stamped by the spawning host describing where the caller process lives. Feed argument defaults (e.g. `pane slot write`, `context current`), caller provenance (`notify`, `app call`), and nested-host launch guards. | Never consulted for profile-dir (`resolve_channel_dir` in `src/config/mod.rs`) or command-socket (`resolve_command_socket_from` in `src/cli/mod.rs`) routing. Stripped by `host start` (`filter_child_env`). |
| `target-routing` | `--socket`, binary channel name (`plexi-<channel>`), `PLEXI_CHANNEL`, `PLEXI_SOCKET` | Select which host endpoint and channel profile directory (`~/.plexi-<channel>`, `.plexi-<channel>`) a CLI invocation addresses. | **Command socket** (`resolve_command_socket_from`): `--socket` > binary channel name (`plexi-<channel>` resolves `~/.plexi-<channel>` endpoint and ignores `PLEXI_SOCKET`) > `PLEXI_SOCKET` (bare `plexi` only) > none.<br>**Profile / workspace channel dir** (`resolve_channel_dir`): binary channel name (`plexi-<channel>` ignores `PLEXI_CHANNEL`) > `PLEXI_CHANNEL` (bare `plexi` only) > `.plexi` default. |

**Transport completion is newline-framed.** The CLI reports socket success only after the complete newline-delimited JSON frame is accepted. The host discards EOF-terminated partial frames, even when the partial bytes form valid JSON. An explicitly reported incomplete-frame transport failure was not dispatched and is safe to retry; a later host response timeout is not proof of non-delivery.

**Completion testing on PR builds:** `just pr-install` skips completion install. To test, manually run `plexi-pr-<N> completions zsh > <path>` and restore after.

## CLI Design Rules

- **Namespace design:** verify a new command belongs in the right namespace. Place it where the noun already lives, not at top level.
- **Clap docs describe the command, not its history.** Do not put ticket or stint identifiers in clap doc comments.
- **Pane naming:** always name panes after spawning them. Every `plexi pane new`, `plexi app open`, split, or new window should be followed by `plexi pane name <id> "descriptive name"`.
- **Tips:** use `print_tip()` from `src/cli/mod.rs`. Never raw `eprintln!`. Respects `config.cli.tips` and `NO_COLOR`.
- **An absent flag must reach the host as absent.** A clap `default_value` on an optional flag means the CLI can never send "unset", so a host-side default is dead code and changing it silently does nothing. `plexi notify --scope` carried `default_value = "global"`, which is why the host's fallback was unreachable. Leave `Option<String>` flags without a `default_value` and let the host resolve the default (`NotifyScope::default()`); map every *named* value explicitly, never by falling through to the host's fallback.
- **Repeatable flags fan out or they error.** A count flag paired with a repeatable value flag (`context sub --agents N --command CMD`) accepts the value once (applies to all) or exactly N times (one each). Any other count is a hard error — never truncate, never cycle. Expand to one entry per unit in the CLI so the host receives an unambiguous list; see `expand_pane_commands`.
- **Resolve the caller's context by `PLEXI_CONTEXT_ID`, not `PLEXI_CONTEXT_NAME`.** Context names are not unique; the id is. Send the id; the host consults the name only when no id was sent (`resolve_parent_context`). An id naming no live context is an error, never a reason to fall back to the name — a stale id plus a name some other context happens to share would silently target a stranger. The same identity is also provenance: a command whose effect is attributed to its sender (`plexi notify`) stamps `PLEXI_CONTEXT_ID`/`PLEXI_PANE_ID` onto the request itself, because the host must never derive the sender from dispatch-time active state; an unresolvable identity widens the effect (notify escalates scope to global) rather than fabricating a home.
- **`plexi skill install` writes the skill embedded in this binary.** `--agent claude`, `--agent codex`, `--agent pi`, or `--agent all` lands `SKILL.md` where that agent CLI loads a user skill. The text is `include_str` of `skills/plexi-cli/SKILL.md` minus sections tagged for experiments that are off, so `plexi_version` matches `CARGO_PKG_VERSION`. Each channel installs to `plexi-cli` (stable) or `plexi-cli-<channel>` and refuses to overwrite a file whose frontmatter `channel:` differs. It does not talk to the host.
- **Experiments own their command paths in one table.** `ReleaseFeature::owned_paths` (`src/release/catalog.rs`) drives help and completions (`gate_command`), the execution backstop (`blocked_feature`, called once after parsing in `main`), and the skill. Add a command to an experiment by adding its path there, never by an ad hoc `exit_if_feature_disabled`. Runtime-only experiments (no command) are listed in the `RUNTIME_ONLY` test constant. The skill generator derives experiment markers from this table; see `skills/AGENTS.md`.
- **`app call` identity is host-stamped and context-scoped.** `plexi app call` sends `PLEXI_PANE_ID` as a claim and `PLEXI_CALL_CREDENTIAL` when the host issued one. The host checks that claim against peer ancestry or the credential. The app sees `pane:<id>`, `mcp:pane:<id>`, or `session:<id>` — never `user`. A forged, missing, or mismatched claim is `permission_denied` and is written to the host log. `--json` prints the structured reply, including `error_code` and `pending_request_id`. `--pane <id>` addresses one instance when several of the same app are open. Every call is admitted by the permission monitor. `plexi assistant permission list|show` is the observation seam. `assistant permission resolve` is refuse-only: the host returns `permission_denied`, writes a `refused_resolve` audit row, and leaves the pending in place. `needs-you resolve --approve` is refused the same way for every kind. A real desktop click on the approval banner is what grants.
- **`plexi needs-you` is the single waiting-on-you record.** Click approvals, agent questions, blocked runs, agent permission-widen requests, integrity alerts, and keychain prompts are one host record (`id`, `kind`, `actor`, `resource`, `summary`, `created_at`, `expires_at`, `run_tag`, `resolution`, `details`, `answer`). `plexi needs-you list --json` prints the open rows after expired ones are auto-denied; `plexi needs-you show <id> [--json]` inspects one row (open or settled) with its structured `details` (`choices`, `allow_free_text`, `preview_refs`, `correlation_id`) and `answer` plus any linked `continuation`. `plexi needs-you ask` files a structured `question` or `blocked_run` item and optionally creates or updates a durable `ContinuationRecord` (`operation_id`, `session_id`, `pane_id`, `context_id`, `resource`, `expected_revision`, `resume_condition`, `state`, `needs_you_id`, `answer`, `execution_receipt`) sealed in `<profile>/host/continuations.json`. `plexi needs-you answer <id> --answer <text>` settles a `question` or `blocked_run` item without minting a `GrantRecord` and is refused (`permission_denied`) from an unauthenticated agent pane unless the caller come from a human terminal outside any host pane or carries the host-minted `PLEXI_PI_UI_ANSWER_TOKEN` from an interactive TUI dialog. `plexi needs-you reconcile [--session-id <id>] [--operation-id <id>] [--json]` returns durable continuation records paired with their `NeedsYouRecord` so a reattaching agent session can resume or report stale-revision failure without duplicate mutation, and `plexi needs-you complete <operation_id> --receipt <json>` marks a continuation `completed` (or `--failed` for `failed`). Open rows are sealed in `<profile>/host/needs-you.json` and listed again after a restart; a journal that fails that seal is an integrity item and is not a grant. Who may settle a row is one broker rule, `NeedsYouKind::surface_may_resolve`, applied by `PermissionMonitor::resolve_needs_you_from` for every surface (desktop click, command socket, phone relay). Socket, terminal, agent pane, and phone: approve is refused (`permission_denied`, row stays open, `refused_resolve` audit row) for every kind; deny is refused for `integrity` and `keychain` and settles every other kind exactly once. Only a real click in the host window approves: the approval banner for click approvals, and the sidebar Needs-you row's Approve/Dismiss (oldest open item that is not a click approval) or the Needs attention review for the rest. Keychain recovery is therefore a desktop click, not `needs-you resolve --approve`. Questions and blocked runs record the resolution (or structured choice/free-text answer) and do not mint a grant. `GET /api/needs-you` on the phone shell reads this same record; `phone_can_approve` is always false, so a phone does not answer questions (the relay is an experiment).
- **`plexi permissions` reads the permission monitor.** `list [--json]` prints persistent grants, persistent denies, time-boxed grants, and pending asks. `reset <id>` clears a stored denial so the next call asks again. `revoke <id>` removes an allow or refuses a pending ask. `allow <id>` turns a denial into an allow. A `PLEXI_PANE_ID`, a `PLEXI_CALL_CREDENTIAL`, or a pane ancestor on this host's socket (`caller_is_pane_agent`) marks the caller as an agent. Reset and allow from an agent, from MCP (`permissions_reset` / `permissions_allow`), or from an Assistant host tool file Needs you and do not change the decision. Revoke is allowed from any caller. A terminal that is not a pane of this host is the human. The Permissions app shows the same rows.
- **Permission files are host-signed.** Enforcement reads `grants.toml` only. A leftover `permissions.toml` is imported once and retired; deleting it does not change a decision. The audit is `permission-audit.jsonl`. The host HMACs `grants.toml` with a key kept in the host seal store (`host_key`, item `permission-mac`), not in `secrets.json` and not under a workspace id. `plexi:host:*` is reserved: a workspace whose id is `host` cannot `plexi secret get` the seal key. A missing or bad MAC, once the seal key has been read, quarantines the file, treats every decision in it as ask, files Needs you with kind `integrity`, and appends an integrity audit row. A keychain read that fails because the key is unreadable (access denied or interaction not allowed, including errSecAuthFailed -25293) is not a bad MAC. The host deletes that item, creates a new seal key whose keychain ACL trusts this app's designated requirement when that requirement is stable across rebuilds, and reseals the profile. Grants that cannot be verified under the new key are reset to empty and loaded. A silent keychain call runs off the UI thread and stops at the startup deadline in `host_key`. If that deadline passes, or the old item cannot be removed without a prompt, Needs you gets one item of kind `keychain` and grants stay unloaded. Startup does not wait on a keychain prompt and does not call `SecKeychainItemSetAccess`. Approving it retries the read with prompts allowed, or rotates and reseals when the old key stays unreadable. Denying it does not load grants. A durable grant that cannot be sealed is not an allow: the user and the agent get an error that the grant was not saved, and the audit does not record `allow_always`. The audit is an append-only hash chain; its tip is in the same host seal store. That store's `get`/`set`/`delete` keep the account string unchanged, so a Needs you journal tip (`plexi:host:needs-you-journal-tip:` plus the sha256 of the profile host directory) uses the same API and the same permission MAC (`mac_key_bytes`, `existing_mac_key`). An edited or deleted line fails that check and files the same alert. The host does not apply permission changes it finds in those files; changes go through the permission monitor. A declared non-sensitive capability with no stored decision is auto-granted as a row in that store. A sensitive capability stays withheld until a human grant. Agent panes do not receive the key, and their environment drops any value that contains the profile directory (`PLEXI_PROFILE`, `PLEXI_CONFIG_DIR`); `PLEXI_SOCKET` and `PLEXI_CHANNEL` stay so `plexi agent report`/`plexi agent done` reach the host without manual exports, while the host authenticates caller pane identity from kernel socket peer ancestry (`resolve_socket_peer_pane`). A process running as the same OS user can still kill or replace the host binary. On Linux the seal key is stored only in Secret Service; if that service is missing the host refuses to seal and does not write a plaintext key. On macOS the item is in the keychain under service `plexi-host-seal`, trusted to this app's designated requirement, so a same-signer rebuild keeps access and `security` does not return it. OS-level sandboxing of agent panes is a follow-up. A restored terminal is not marked as an agent, so it receives the socket again.
- **`plexi app tools` reads the live tool registry; `plexi app info` distinguishes live from manifest-only tools.** `plexi app tools [--app <id>] [--context <id>] [--json]` queries the running host over the command socket for the live tool registry scoped to the context (`ToolDispatcher::from_registry` / `snapshot_for_caller` shape: qualified tool name, owning `app_id`, `pane_id`, description, and full JSON `parameters` schema). `plexi app info <id>` populates its tools section from that live registry when an instance of `<id>` is running in the caller's context (`Tools (live registry, pane <N>):`), and explicitly labels the static `@tools.tool` source scan `Tools (manifest-only; static source scan, app not running in context):` when the app is not running or the host is unreachable. The Assistant reads the static scan alongside the live clap tree, open panes, and permission monitor through `host.introspect`. There is no separate help document.
- **`relay` is the phone-link noun.** `relay enable` stores the websocket URL and the host owns that socket after startup. `relay connect` attaches to the host socket or refuses; it does not open a second one. `relay pair` adds another phone. Pairing is confirmed by a desktop Allow once click on the permission sheet. `relay confirm` from an agent pane is refused. `ws://` is accepted only for loopback. The relay forwards `submit_assistant_turn` and carries no grant, approval, or permission field. Phone turns use a caller-owned conversation unless the phone opts into the desktop transcript. Approving a permission from the phone or the terminal is `permission_denied`. Only a desktop Allow once click grants.
- **Agent-facing commands answer in one round trip.** A command that creates addressable objects returns their ids in its JSON response (`context sub` → `{"context_id","windows","panes":[…]}`), so the caller never needs a follow-up `pane list` to act on what it just made.
- **Blocking orchestration verbs answer from the host, never a CLI sleep loop, and `pane --help` signposts the two-command agent recipe up front.** `pane send --submit`, `pane new --agent`, `pane slot wait`, and `pane message recv --wait` park their reply host-side (`src/app/pane_wait.rs`), serviced from `App::logic` with a host deadline strictly below the CLI's poll window so the caller always sees the host's typed reason, not a generic client timeout. Exit codes are the contract — `0` confirmed outcome, `2` timeout (distinct, branchable), `1` usage/plumbing — and stdout carries only the payload (pane id, matched value, or drained JSON message array). Waits are level-triggered: a condition already true at call time answers immediately. `plexi pane --help` signposts the canonical two-step "Driving an agent in another pane" recipe (`pane new --agent` to boot, `pane send --submit` to brief — two commands, no sleeps, no capture polling); `pane new --help` promotes `--agent` up front as the supported way to launch an agent where a printed id means ready-to-brief; and `pane send --help` and `pane key --help` cross-reference `--submit` for confirmed submission. A new wait-shaped verb follows this pattern; never add a CLI-side poll loop wearing a blocking coat.
- **`pane message send`/`recv` is the sanctioned inter-agent FIFO mailbox.** `plexi pane message send <id> "<payload>" [--submit]` appends a structured message (`id`, `from_pane_id`, `to_pane_id`, `payload`, `timestamp_ms`) to the target pane's host-managed in-memory `VecDeque` without clobbering prior messages. Sender identity (`from_pane_id`) is derived host-side from the socket peer's process ancestry (`capture_peer_ancestry` → `resolve_socket_peer_pane`), never self-reported by the CLI. The command prints a JSON ack with `status` (`"delivered"` when a parked `recv --wait` waiter consumed the message immediately or `--submit` woke an idle agent; `"queued"` otherwise), `message_id`, `queue_len`, and `woke`. When `--submit` is passed and no waiter consumed the message immediately, the host checks `agent_reports_idle(pane_id) && !submit_in_flight(pane_id)`: if idle, it types a short wake prompt (`[plexi message from pane <sender>] run \`plexi pane message recv\``) and registers a `PendingSubmit`; if working or a submit is already in flight, it leaves the PTY untouched and queues the message. `plexi pane message recv [pane_id] [--wait --timeout N]` (defaulting to `PLEXI_PANE_ID`) drains the pane's mailbox as a JSON array; with `--wait`, it reuses the `slot_wait` mechanics (`PendingMessageRecv` in `src/app/pane_wait.rs`, serviced in `App::logic`) to block host-side with zero polling and exit `0` with the JSON array, `2` on timeout, or `1` on error. Closing a pane clears its mailbox and fails any parked `recv --wait` with exit `1`.
- **Lifecycle consumers share the brokered event connection.** `pane wait` and `pane events --follow` use `app::event_stream` and the existing timeline subscription queue. Register before reading the current snapshot, retain each connection's own delivery identity, and release it on completion or disconnect. CLI-facing predicates and record semantics are documented in `skills/plexi-cli/SKILL.md`; lifecycle records are defined in `host::pane_lifecycle`.
- **`pane command --enter` shares `pane send --submit`'s settle → Enter → confirm path.** Writing `<cmd>\n` as one raw blob races an interactive shell's completion/autosuggest machinery for the Enter (stint 0654; observed as an ambiguous-prefix alias opening a completion menu instead of running). `--enter` therefore maps 1:1 onto `SendToPane { submit: true }` — the exact request `pane send --submit` issues — through `cli::pane_send_cli`, not a second settle implementation. It is scoped to terminal panes only (an app pane refuses `--enter` the same way it refuses `--submit`), and its exit code is the same contract: `0` confirmed submitted, non-zero typed-but-unconfirmed with the observed input line on stderr. Without `--enter` it stays the plain type-only verb (`submit: false`).
- **Background host launch is explicit boot state.** `plexi host start --background` launches without activating Plexi; on macOS it uses Accessory policy and has no normal Dock or menu-bar presence. The flag is forwarded through a launch-only env var that the host consumes at process entry, before it can reach terminal/app descendants; the CLI also strips it before explicit re-add, so background mode never cascades into a nested `host start`. It is not configuration. App Nap exemption remains unconditional. Pane send/key/click and `pane focus` operate inside the host through egui/PTY paths and do not request OS activation; `pane focus` changes focus within Plexi but does not front an Accessory app.
- **Pane capture cursors account for screen redraws, not only shell linefeeds.** Full-screen alternate-screen TUIs repaint rows in place while leaving the terminal cursor on the same line. `pane capture --from-cursor` must advance for those redraws and return the changed rows; `--plain` prints only captured lines on stdout and puts the next `cursor=<N>` on stderr. The default JSON envelope stays unchanged.
- **`pane state` separates the agent's claim from the host's observation, and neither is reachable without the other.** A pane's `status` slot is a claim an agent writes about itself; it is not liveness — a wedged agent can sit for hours with that slot still reading `running`. `plexi pane state <id>` therefore always returns `claimed_state` (the `status` slot's raw value plus its age, agent-authored, `null` if never written) and `observed_state` (host-derived: process alive, seconds since last output, child pids via `pgrep -P`, current foreground command) together, computed by the single accessor `crate::host::pane_liveness::compute`. `--stale-after <secs>` raises a typed `stale_claim` when a claim exists but no output has been observed within that window; omitted, no default is invented and `stale_claim` stays `null`. Restart policy and event-bus lifecycle transport are out of scope for this primitive (0628, 0664).
- **Pane status is the host-owned corroboration path.** `pane status <id>` combines the shared agent detector, the TUI status bar, and the trailing buffer line into `working | idle | blocked | unknown` plus `high | low` confidence and the raw evidence. Working agent state and a trailing tool call are authoritative; idle requires all signals to agree; a truncated status bar can never prove the busy marker is absent.
- **Pane heartbeats are host-owned.** `pane heartbeat <id> --every <duration> --text <text>` schedules type-and-submit work in `App::logic`; it never sleeps or loops in the CLI. The default only fires on idle agent panes, `--off` removes it, and status/list report its additive state.
- **Boot state comes from the agent detector, never a PTY regex.** `pane new --agent` blocks on the pane's `PaneAgentState` reaching idle through `Pane::agent()`, which merges the detector's two signal sources: hook reports (`SetAgentState`, authoritative once any hook fires) and the host-observed synthesis in `tick_terminal_activity` (known agent binary in the PTY foreground + output settle — required because Codex defers `session_start` to the first prompt submission, so a freshly booted Codex never self-reports). New agent support goes into that one detector (`known_agent_process`, the hook installer), never into a parallel prompt-signature scraper.
- **Reported agent identity is human-facing.** The `agent report --agent` name and `--detail` active tool appear in Cmd+P across all contexts. Same-name agents are distinguished by their one-based position within the context, so repeated squad commands remain navigable.
- **Agent runs and delegation use the one permission gate.** An agent card under `<workspace>/.plexi/agents/<id>/` stores declared tool grants (`tool=allow[:hard|:soft]|ask|deny`, where `hard` persists until revoked, `soft` expires after `[permissions] soft_grant_days` in `config.toml`, default 30, reverting to `ask` and appending an `expire` row to `permission-audit.jsonl`, and legacy `grants.toml` entries without `kind` default to `hard`). `AGENT.md` is guidance and grants nothing. `spawn_run` claims a run: the same `admission` returns that run, and a different admission while it is active is `assignment_conflict`. `finish_run` stops that run (and revokes any run-only grants) so another admission can start. The host appends the run through the AI ledger with `client_ref`, `kind`, and token counts. `delegate` starts a temporary child whose grants must be a subset of the parent run; any broker refusal (ungranted tool on `delegate`, or a member calling a denied/ungranted tool) appends a `deny` row to `permission-audit.jsonl` and files one `permission_request` item in `plexi needs-you list` carrying requester `pane_id`, `tool`, and `parent_run`. Resolving that item with Allow from the desktop (click-only approval rules from 0788 apply) grants that tool for that run only (`runs.jsonl` + session-bound `GrantRecord`), never permanently on `agent.json`. Tool execution is the host MCP endpoint (`agents.list`, `agents.create`, `agents.delegate`, `agents.ping`, `agents.review`, `agents.admin`) admitted by `PermissionMonitor::admit`. An ask-tier call shows up on `plexi assistant permission list`. The desktop banner or the Permissions app decides it. `assistant permission resolve` from the terminal is refused. A run token is that run's MCP bearer. A pane credential does not execute these tools. `plexi command-view` lists every registered agent and run from those records; `command-view open` paints the same projection. `plexi command-view cancel <run>` stops that run before the next tool. `command-view resolve` and `command-view allow` do not grant, and both refuse when `PLEXI_PANE_ID` is set. `plexi app open command` and `plexi app open command-view` open that pane. `command-view --follow` streams `command.view` from publisher `plexi.host.command`. Parent-to-child delegation only narrows grants.
- **Lifecycle facts survive the status projection.** `agent report --event` retains the raw provider event separately from working/idle/blocked; `--blocked-reason` carries an explicit typed reason. The shared hook script passes raw events through the invocation-scoped `PLEXI_AGENT_EVENT` variable so older channel CLIs still accept its arguments. Reports without provenance remain supported and are labeled legacy reports. The event contract lives in `src/host/pane_lifecycle.rs`.
- **Worktree isolation is a host-managed pane primitive via `wtp`.** `plexi pane new --worktree <branch>` creates or attaches an isolated git worktree through `wtp` (`src/host/worktree.rs`, never raw `git worktree` or `rm -rf`), records its initial `HEAD`, starts the terminal pane rooted at the worktree path, and exposes `"worktree": {"branch", "path", "repo_root"}` on `pane info` / `pane list`. When the pane closes (`pane close`, UI tile close, or context deletion), `PlexiApp::reclaim_pane_worktree` inspects git cleanliness and `HEAD` movement: a clean worktree whose `HEAD` has not moved is removed via `wtp rm <branch>`, while a worktree with uncommitted changes (`dirty`) or new commits (`ahead`) is retained and its path and reason are logged and returned in the `close_pane` reply (`retained worktree: <path> (dirty|ahead)` on `plexi pane close <other-pane-id>`).
- **`pane result` is the schema-validated write-once structured return contract for an agent pane.** Spawners declare a JSON Schema at spawn (`plexi pane new --result-schema <json-or-path>`) (the brief-time `pane result schema` verb was removed; declare it at spawn); the CLI resolves file paths against the caller's cwd and validates the schema before sending it (`host::pane_result::parse_schema_spec`). The worker agent writes its structured JSON object once through `plexi agent done --result <json>` (the `pane result write` verb was removed) (not scrollback or an unvalidated slot). The host validates the payload against the declared JSON Schema synchronously (`host::pane_result::PaneResultState::try_write`) and rejects malformed or schema-violating payloads back to the agent (`exit 1` with `error_code: "invalid_result"` and the validation error on stderr) while leaving the result uncommitted so the agent can self-correct; once a valid JSON object is committed, subsequent writes or schema changes are rejected with `error_code: "result_already_set"`. Reading via `plexi pane result <id> [--wait --timeout N]` returns the validated JSON object on stdout (`exit 0`), distinguishes "no result yet" (`error_code: "no_result_yet"`, or `timeout` when `--wait` expires — `exit 2`, empty stdout) from "last write was rejected as invalid" (`error_code: "invalid_result"` — `exit 1`, empty stdout), and retains the committed result across pane close so ephemeral workers' returns remain readable.
- **One registry-backed agent model (`AGENT.md` + `settings.toml`), multi-CLI harness adapters, unified interactive spawning, unspoofable provenance, queued `agent done` delivery, self-closing sub-context squads, 2-tier escalation, lazy Standby startup restore, and closed-run history.** An agent is a directory `<agents-dir>/<slug>/` containing `AGENT.md` (the system prompt / persona markdown) and `settings.toml` (`name`, `description`, `[harness]`, plus optional `default_tier` and `[permissions]`; `#[serde(deny_unknown_fields)]` on `[harness]`: `cli`, `fallback`, `model`, `ephemeral`, `result_schema`). Agents live in two tiers resolved by `AgentRegistry::load_with_optional_workspace` via `resolve_agent_lookup_workspace_root` (walking up from `cwd` for `.plexi/agents` or `<channel-dir>/agents`, stopping at `workspace_walk_stops()` so `$HOME` never masquerades as a workspace): workspace (`.plexi/agents/<slug>/`) overrides global (`<profile>/agents/<slug>/`). `plexi agent create <slug> --cli `resolve_agent_spawn_location`), snapshotting the agent's `settings.toml` `[permissions]` posture onto the worker pane (intersected with any parent pane's posture so a child never widens its parent's <AGENT.md>` on `pi` and `claude`, `-c developer_instructions=...` on `codex`, or `--prompt-interactive` on `agy` with the `# Plexi worker contract` (and any `result_schema`), stamping `PLEXI_PARENT_PANE` and `PLEXI_EPHEMERAL`, and recording unspoofable `spawned_by` provenance (`"human" | "agent:<name>" | "team:<team>/<run_id>" | "system"`, derived from socket peer ancestry, exposed `<workspace>/.plexi/results/<pane-or-run-id>/RESULT.md` and `result.json` (inspectable via `plexi agent result [<pane>] [--json]` even after pane close or host restart), files a `NeedsYouKind::AgentDone` attention item (`"<agent> done: <summary>"`, keyboard-actionable with `Cmd+Alt+P` then `Enter` to open `RESULT.md` in a `text-editor` split) and fires an OS notification when `agents.os_notifications` is on for human-started agents (no parent agent), queues a `QueuedChildResult` on the parent pane when the parent is mid-turn (delivering all queued child results as one batched turn when the parent next reports `Idle`, or draining on `plexi agent wait <child...>` without duplicate delivery, and showing `"N results waiting"` in the parent pane header), and closes ephemeral panes when `ephemeral = true`. Escalation is 2-tier: Tier 1 (`AgentState::Blocked` / `plexi agent ask "<question>"`) writes the `question` slot and wakes the `parent_pane_id` master agent waiting on `plexi pane wait` without filing a human `NeedsYou` item when `parent_pane_id` is set; Tier 2 (`AgentState::NeedsYou` / `plexi needs-you`) escalates to the human. `ContextState::compute` rolls up child status onto the parent `PortalPane` with precedence `NeedsYou > Blocked > Error > Working (Active) > Idle`. `SavedPane` persists `slots` and `agent_session: Option<SavedAgentSession>` (`harness`, `config_name`, `session_id`, `last_state`, `last_blocked_reason`, `last_detail`, `parent_pane_id`, `spawned_by`, `ephemeral`, `tail_preview`, `standby_scrollback_tail`), marking the workspace dirty on any `session_id`, `state`, or `slots` mutation. On startup (`[agents] restore_mode = "lazy" | "eager" | "off"`, default `"lazy"`), ephemeral `Completed` panes are skipped, mid-turn `Working` panes transition to `Interrupted` with their `tail_preview`, active-context panes auto-resume via their Harness Adapter, and background/sub-context panes enter lightweight `[Plexi Standby]` with their saved scrollback tail. Standby panes resume only on `Enter` or explicit `plexi pane send` input; focusing or clicking keeps them in Standby. Closing any agent pane appends an `AgentHistoryRecord` to `<profile>/agent_history.jsonl`; `plexi agent history [--limit N] [--harness <name>] [--role <name>] [--json]` inspects closed runs offline and `plexi agent reopen <run-id|session-id> [--subcontext <name>] [--json]` spawns a new terminal pane resumed into the historical session's `cwd`, `slots`, and harness resume command.

- **`plexi run` layers global and workspace commands per name, supports chained `steps` + `on_load`, and exposes `--json`.** Resolution follows five rules: (1) global tier is `config_dir().join("commands.toml")` (`~/.plexi-alpha/commands.toml`, `~/.plexi-beta/commands.toml`, `~/.plexi/commands.toml` on stable) plus executable files in `config_dir().join("scripts/")`; (2) workspace tier is `<workspace>/.plexi-<channel>/commands.toml` (`.plexi/commands.toml` on stable), where `<workspace>` is the nearest ancestor of `cwd` containing `.plexi-<channel>/` via `registry::resolve_workspace_root_stopping_at` (stopping at `$HOME` and login home so `~` is never a workspace), with fallback to `cwd` itself if `cwd/.plexi-<channel>/commands.toml` exists and is distinct from the global file (`cli::resolve_commands_workspace_root`); (3) the command palette resolves from the focused pane's `cwd` then the context root (`effective_commands_workspace_root`), `[keys]` `"<chord>" = "run:<name>"` bindings use the adopted/host workspace root else the context root (`run_user_command_by_name`), and `plexi run` uses the shell `cwd`; (4) precedence per command name is workspace `commands.toml` > global `commands.toml` > global `scripts/` (`resolve_user_commands`); (5) files are re-read on every palette open and every run with no restart needed. `plexi run` lists both tiers tagged `[workspace]` / `[global]` (or prints the resolved workspace and global `commands.toml` paths when none are defined), and `plexi run --help` appends the active channel's resolved workspace, global, and scripts paths; `plexi run --json` emits `[{name, scope, description, run, steps, on_load, secrets}]` where `secrets` carries injected secret names only (never secret values). `[commands.<name>]` accepts either `run = "..."` or `steps = [...]` (mutually exclusive; each step is a Plexi CLI subcommand such as `"pane new --right -- mixer"` / `"pane new --down -- nooise --mute"` or a shell snippet, with `$1`, `$2`, ..., `$@` substitution) plus optional `on_load` steps (`pane new --on-load <step>` reuses the same step runner `run_steps_with`); steps run sequentially and stop at the first failure reporting `step <i>/<n> failed: <cmd> (exit <code>)`. `[keys]` in `config.toml` binds chords to user commands (`"<chord>" = "run:<name>"`), validated against `reserved_host_shortcuts` by `plexi config check`. In the command palette, `Edit commands` (`PaletteCommand::EditCommands`) opens the effective workspace or global `commands.toml` in a `text-editor` split (creating it from `COMMANDS_TEMPLATE` via `ensure_commands_file` if absent) and hot-reloads on the next palette open.
- **Notes resolve their tier from the working directory, never from
  `PLEXI_CONTEXT_ROOT`.** `plexi note` writes into the tier of cwd's nearest
  anchored ancestor (the nearest directory holding a `.plexi/`), falling back to
  the global tier when nothing above is anchored. `plexi note list` rolls up that
  tier, every tier nested below it, and the global tier, through the same
  `notes::notes_scopes_for_root` the GUI picker calls — so the two surfaces list
  the same notes by construction. The env var is stamped at pane spawn and a parent
  cannot mutate a live child's environment, so it goes permanently stale after
  `plexi context set-root`; see `src/host/AGENTS.md`. `note open` builds its fzf
  candidate list by shelling `plexi note list`, so ordering and tier resolution
  have exactly one implementation, and it fails loudly — never printing a directory
  instead — when fzf, a pane, or a host is missing.
- **`plexi demo` is macOS-only until platform keymaps exist.** On Linux and
  Windows it refuses before teaching any shortcut; do not infer or document a
  replacement chord until the host keymap defines one.
- **`plexi ledger` prints per-client totals from the local AI ledger.** It
  does not talk to the host. With no subcommand it is the human summary
  grouped by client. `ledger summary --by client` (used when `--by` is
  omitted) or `--by kind` groups rows; `--since` is a `YYYY-MM-DD` or RFC3339
  lower bound on each row's timestamp. Rows written before run tags existed
  are migrated in place to explicit null `client` and `kind` and still count.
  A token count is a positive number or the word `unknown`. A missing or zero
  reading stays `unknown` and is left out of a group total. `--json` prints
  the groups with the same token contract. `assistant send --client` and
  `--kind` are per-run overrides; an omitted flag stays unset so the host can
  apply `[ai] client` and kind `output`. `assistant send` does not require an
  open Assistant pane: the host reuses one in the context or creates a hidden
  one. A `--pane-id` that does not exist still fails.
- **`plexi debug session` reads the session flight trace, not the host.** The host's `host::flight_recorder` writes `<profile>/sessions/<sess-id>.jsonl` (envelope `{seq, ts, host_session_id, context_id, pane_id, call_id}` plus `kind` and `data`) from taps in `app_timeline`, `tool_dispatch::dispatch_call`, the permission monitor's audit path, and `event_log`/`FileEventSink` and the CLI invocation transport; `latest.jsonl` points at the newest. `list` and `show` are file reads, so they work after the host exits. `show --pane` keeps rows for that pane plus the calls it made (permission rows carry only a `call_id`). `--join-agents` resolves recorded `Provenance.session_id` values to transcripts under `~/.pi/agent/sessions` and `~/.claude/projects` and merges them by timestamp; a missing transcript warns and is skipped. The trace never changes `permission-audit.jsonl` or `grants.toml`. History display, timezone selection, capture redaction and pane-scoped review-only draft workflows are documented in `skills/plexi-cli/intro.md` under Draft a workflow from a session.
- **Routines are post-v1.** `plexi routine` stays compiled for beta and
  worktree development but is release-gated and hidden from stable help.
- **A pane's `plexi secret get` waits for a desktop click.** When `caller_is_pane_agent` is true the CLI never opens the store: it sends `pane_secret_get` and the host (`serve_secret_get`) names the caller from the socket peer's ancestry, not from a claim. A caller that resolves to no pane is `permission_denied`. The host admits tool `secret.get` (resource `NAME@<workspace root>` or `NAME@global`, `read_pane_secret`); without a grant the CLI prints `permission_required` and `pending_request_id=` (exit 2) and the desktop banner shows the ask. A reply that carries a value is written `0600` into the profile `rpc/` directory only, and the host deletes it after a short TTL in case a sandboxed caller could not. An unreachable host is `permission_denied`, never a local read. An approved retry ends with a value, not-set result, or a terminal backend/authentication error; it never requests another banner internally. Keychain authentication runs off the host event loop and the CLI permits time for the system dialog. Secret workspace discovery uses the registry home exclusions and bounds its result to the pane context. `secret set` does not add the name to `[terminal.env] inject`; it prints the names `secrets.toml` already injects, and `secret list` marks them. Agent panes (`PaneLaunchSpec.agent`) receive no workspace or folder secret in their environment (`withhold_terminal_secrets`).
- **`plexi secret list`, `doctor`, and `ai doctor` reconcile the secrets index against a keychain scan before reading.** `reconcile_secrets_before_read` ensures the plaintext index matches the OS credential store (a failed scan warns and degrades to the index); the doctor checks read the canonical `OPENROUTER_API_KEY` account only.
- **Folder secrets stay out of the profile plaintext.** `plexi secret set NAME --folder <path>` stores a directory-scoped secret through `folder_store` (contract: `src/workspace/AGENTS.md`). `secret list` prints names and folders. `secret rm` removes one binding. `secret read` admits through the permission gate and prints `permission_required` (exit 2) until a grant exists. `secret grant` does not write that grant: it prints `permission_denied`, audits the name and folder, and never reads the value. `grant_folder_secret` remains the host function that records an allow. `secret exec --cwd` runs `shell::build_env` only for a caller that is not a pane of this host; a pane, including a child that cleared `PLEXI_PANE_ID` while its ancestor still names this host's socket, gets `permission_denied` and the command is not started. A pane-requested terminal spawn withholds folder secrets. The value is never logged.
- **Human-owned panes carry user authority scoped to their context root; agents are still narrowed by grants.** A human-owned pane (`TerminalPane::is_human_owned` / `PlexiApp::is_human_owned_pane`) is a terminal pane whose session the host spawned directly for the user, with no bound team member, no agent harness/role, no `parent_pane_id`, and `agent_spawned == false` (`PLEXI_AGENT_SPAWNED` unset). Any pane launched with `--agent`, bound to a team member, or spawned from an agent pane (including a plain shell created by an agent via `plexi pane new` or `HostAction::OpenPane`) is marked `agent_spawned = true` (`PLEXI_AGENT_SPAWNED=1`) and never qualifies. In `create_agent` (`src/agent/runs.rs` and `src/app/team.rs`), a human-owned pane's parent grant set is the user's authority for its context root (`user_context_authority_grants`), so creating an agent from a human pane in its own context succeeds (`ok: true`) without filing a `needs-you` request, while the created agent receives only its declared grant set (and cannot exceed those grants at tool-call or delegation time). An agent-spawned pane without a card still uses `pane_session_grants` from desktop approvals, and card-bound panes keep `card.grants`. Context scoping is enforced across `agents_api` and secrets (`pane_may_access_context_root`, `enforce_pane_context_scope`, `serve_secret_get`): subdirectory contexts are isolated units, so a pane in context A has no authority over context B's agents, grants, or secrets — including when B is nested inside A's directory. This is a Plexi API (`agents_api` / host tools), secrets, and grant-scoping boundary, **not** an OS file-access boundary: a process in the pane still runs as the OS user and can read or write any file the OS user can.

- **Names-only secret inventory can be partial.** `secret list` returns user-scope names when cwd is outside the pane context, with workspace exclusions in `skipped`. JSON is an object containing `entries` and `skipped`. Folder entries match cwd ancestors within the admitted scope; disabled folder entries are counted, never silently omitted. `secret list --context` asks the host to resolve an owned context by id, name or root and authenticate the socket peer. Human-owned panes may list that context; agent panes require a names-only `secret.list` grant through the permission monitor. Value reads and writes retain their existing scope checks.
- **Check experiment gates before consuming clap matches.** `FromArgMatches::from_arg_matches_mut` removes argument evidence; the gate must run before conversion. Missing experiment-arg values are retried only for the gate diagnostic. Hidden args retain an experiment explanation in their parent's help.
- **Restarting the caller host needs confirmation.** `host restart --yes` starts a setsid-plus-double-fork coordinator when invoked from a pane of that host, so neither the caller pane's process-group teardown nor host reparenting can interrupt it. The coordinator uses the same explicit, scrubbed environment as `host start`: it removes the old host session marker and every pane identity/routing credential, then adds back the resolved channel while retaining ordinary launch environment. It logs its wait, old-host exit, launch, and resulting pid to the channel log. That caller receives a restart acknowledgement; external callers wait for the new pid and pane count. No seed panes are supplied, so saved workspace restore applies.

## Documentation Rule for CLI Changes

MCP visualizer launch and consent follow [`MCP_APP_CONTRACT.md`](../render/MCP_APP_CONTRACT.md).
Keep the CLI, named MCP prefix, and palette launch paths id-based.

`app call --wait-approved` holds the exact request for a bounded desktop decision,
then re-admits and executes it once. It observes consent; it cannot grant it.
Denial, timeout, or caller exit ends the wait without execution. Without the flag,
an ungranted call still returns `permission_required` immediately. Session approval
may vary arguments only within the same caller, tool, app instance, workspace,
context and resource; it ends when Plexi quits and is revocable in Permissions.

Any change to a CLI verb, flag, or agent-facing behavior updates this file **and** `skills/plexi-cli/SKILL.md` in the same PR. Regenerate the skill following `skills/AGENTS.md`; edit `skills/plexi-cli/intro.md` when a workflow changes. Shell completions are generated from the clap tree (`completions_cli`), so a new flag needs no hand-written block; verify with `plexi completions zsh | grep <flag>`.

`agent team run` resolves a workspace team first, then the active channel
profile and built-ins. It may run global or built-in teams without a workspace;
those runs use the profile scope and default to its `sessions/teams/` directory.

Shell completion installation and missing shared-hook recovery follow
[`scripts/DISTRIBUTION.md`](../../scripts/DISTRIBUTION.md).

Host launch, restart, updates, doctor and uninstall resolve the native distribution

## Traps

- **Agent tool requests must be stamped as protocol variants.** `agent_tool_cli` validates and serializes `AppRequest` before transport. Do not inject shared JSON fields across command variants: `AgentCall` owns `cwd`, while `AgentMessage` does not. Socket regression coverage lives in `agent_tool_message_cli_socket_round_trip_and_wait`.

- **Windows detached launch must disable handle inheritance.** NUL stdio alone leaves inherited capture-pipe writers in a child, so the caller can wait for EOF after the CLI has exited. `host::windows_launch` owns the no-inheritance process boundary. Host readiness is a deadline-bounded application round trip; an open pipe alone is not readiness.

- **Path-based app commands must not resolve a workspace.** `app validate <path>`, `app install <path>`, `app run <path>`, and `app init --adopt <dir>` operate on an explicit filesystem path. Never call `resolve_workspace_root` for that argument. Use `std::fs::canonicalize` directly (`app_adopt` validates the directory via `load_local_app` and writes only `plexi.scaffold.toml` without touching existing source files). `resolve_workspace_root` is only legitimate in `AppRegistry::load` and new-app `app init <name>`.
- **Profile reconciliation is narrowly scoped.** `app prune --dry-run` reports only positively identified retired first-party pre-v3 installs; never infer deletability from absence from the current core pack, because user and marketplace apps also live in the global profile.
- **Building a `-c` command string:** use `cmd_from_args` (in `src/app/mod.rs`), not `shell_join` directly. A single-arg array is already a shell expression; `shell_join(["echo hello"])` yields `'echo hello'`.
- **Shell suffix construction:** when appending a stay-alive or exec suffix to a user command string, use the absolute shell path from `settings.shell` (already resolved), not `$SHELL`. `trim_end_matches([';', ' '])` the user command before appending to prevent `;;` syntax errors.
- **`PLEXI_CONTEXT_ID` is a spawn-time stamp, never the answer to "which context am I in".** A pane moved by `context push` keeps its old value forever (a parent cannot mutate a live child's environment). Commands that *report* the caller's context ask the host by `PLEXI_PANE_ID` (`context current` → `get_pane_info`, which carries `context_id`/`context_name`/`context_description`), the same truth as `pane info`. The env id is only a request field the host validates (`resolve_parent_context`). `pane list --current` still reads the env id — same class, not yet migrated.
- **The relay control listener is loopback and unauthenticated.** `relay confirm`, `relay pair`, and `relay revoke` talk to the desktop session on `127.0.0.1`. Do not bind that listener on a non-loopback address.
- **Accepted relay control sockets inherit nonblocking mode on macOS.** `read_control_frame` resets blocking mode and reads a complete newline-delimited JSON frame under one deadline. A read timeout alone cannot wait on a nonblocking socket; treating `WouldBlock` as EOF loses commands. Control callers must check the acknowledgement, not just a successful TCP write.
- **Verbs that act on a caller-named id must round-trip.** `context zoom <id>` sends a `response_file` and the host replies `{"error"}` for an id naming no live context; fire-and-forget (`send_to_socket`) cannot report a bad id, so it exited 0 silently. Use `request` + `check_reply_error`.

## Fleet inspection
