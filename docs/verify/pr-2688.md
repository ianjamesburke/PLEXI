## Chess `cargo test` flake

Verdict: test isolation. The same tests pass in one thread and fail when several chess harnesses run in one `cargo test --bin plexi` process.

```bash
cargo test --bin plexi -- --test-threads=1 chess
```

```text
test result: ok. 5 passed; 0 failed; 0 ignored; 0 measured; 2567 filtered out; finished in 27.13s
```

`permission_gate_real_chess_all_ingresses`, `chess_receipt_survives_lost_reply`, `second_chess_pane_routes_by_instance`, `agents_chess_approval_scene`, and `chess_tool_path_commits_publishes_and_rejects_bad_mutations` all passed.

```bash
cargo test --bin plexi -- --test-threads=4 chess
```

```text
test result: FAILED. 1 passed; 4 failed; 0 ignored; 0 measured; 2567 filtered out; finished in 58.57s
```

`second_chess_pane_routes_by_instance` passed. The other four failed:

- `chess_receipt_survives_lost_reply` and `chess_tool_path_commits_publishes_and_rejects_bad_mutations`: `tool_not_found: no tool named "chess__chess.play" in registry` where the test expected a gate result.
- `permission_gate_real_chess_all_ingresses`: `timed out waiting for a chess reply` (`pump_until`, 40s).
- `agents_chess_approval_scene`: scene step `chess_approval wait` returned `approval_timeout` (`attributed or stale result did not appear`) after the pending sheet and Allow once had matched.

A second parallel run, adding `app_call_and_mcp_are_gated_and_audited`, finished `2 passed; 4 failed` in 59.47s. Which tests failed changed:

- `app_call_and_mcp_are_gated_and_audited` passed. `agents_chess_approval_scene` passed.
- `second_chess_pane_routes_by_instance` timed out waiting for a chess reply.
- `chess_receipt_survives_lost_reply` and `chess_tool_path_...` failed again with `tool_not_found`.
- `permission_gate_real_chess_all_ingresses` got a committed `e7e5` (`revision_after` 2, `operation_id` ending in `-stale`) from the assistant path that must return `stale_revision` (`permission_gate_tests.rs` `run_ingress`).

`GLOBAL_REGISTRY` in `src/plexi_ai/tool_dispatch.rs` is process-global. `namespaced_snapshot_for_caller` keeps every registered pane whose `evaluate_reach` owner context equals the viewer context. `PlexiApp::new_for_test` gives window 0 `context_id` 1, and `evaluate_reach` allows that match, so concurrent harnesses look like several chess instances in one context. `select_app_tool` drops the bare `chess__chess.play` name when more than one owner is visible, and returns that bare name when the snapshot has no owner yet; `dispatch_inner` then answers `tool_not_found`. `AppPane::drop` calls `unregister`, so a `--test-threads=1` run does not overlap. `reserve_pane_id_block` already keeps pane ids disjoint (stint 0724). This failure is the shared context id plus the shared registry, and the shared `CPYTHON_MODULE_CACHE` lock under several wasm guests. `chess_tool_path_commits_publishes_and_rejects_bad_mutations` already moves its harness to a unique context id and still fails only in the parallel run.

One installed host is one process and one registry. `second_chess_pane_routes_by_instance` is the same-context behavior, and it passes alone. The full `cargo test --bin plexi` suite was not re-run; the named tests are enough to see the flake and the serial pass.
