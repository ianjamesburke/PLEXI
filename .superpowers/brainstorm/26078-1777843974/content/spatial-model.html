The Spatial Model

One layout string. Pane = context. Overlays are owned by their pane and zoom with it.

layout= values — one param, all cases
"split_v"tile below current pane "split_h"tile right of current pane "split_above"tile above current pane "split_left"tile left of current pane "overlay"full-window centered modal — over everything "overlay_pane"anchored to triggering pane only "background"no UI, runs behind the scenes
Same string on all three callers: plexi CLI, DrawCommand::SpawnPane, AppCommand::SpawnApp
Quick note = overlay + TextInput app. No special infrastructure. plexi open quick-note → layout "overlay". The text input you love is just egui's TextEdit in a minimal app wrapper. Quick note becomes the first proof that the overlay pattern is general.

On AppCommand vs DrawCommand — the honest answer
Why the seam exists
Native apps (file browser, quick note) live inside the host binary. They use AppCommand because there's no wire protocol — they're in-process Rust. DrawCommand is the JSON wire format for external SDK processes.
What actually matters
The seam is invisible to callers. CLI, agents, and SDK apps all use the same socket + same message format. The host routes it internally. Long-term: rebuild native apps in the SDK → AppCommand disappears. Don't chase it now — it's a refactor, not a feature.
The "two videos side by side in one pane" case: That's multiple overlay_pane apps in the same pane. The host needs to tile them within the pane's overlay layer. This is real and doable, but it's a separate problem from the base overlay primitive. Don't block on it — design the pane-ownership model correctly now, and multi-overlay layout follows naturally.
