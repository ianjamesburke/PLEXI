File Browser: Core Mental Model

The root cause of the cd-injection bug is a design choice: how should the file browser relate to terminals? This decision drives everything else.

Current behavior (broken): Navigating in the file browser writes cd '...' as raw bytes into the linked terminal's PTY — even if Claude Code or another process is running there.
A

Fully Independent

File browser is its own thing — like Finder. No automatic CWD sync in either direction. You open it at any path you want. An explicit action (T key or button) opens a new terminal pane at the current directory.

Pros

  • Zero injection risk
  • Clear mental model
  • Works even with Claude Code open

Cons

  • File browser and terminal drift apart
  • Have to manually navigate both
B

One-Way Observer

Terminal cd → file browser follows automatically. But navigating in the file browser never affects the terminal. You explore freely; terminals are untouched. Explicit T to open a terminal at current path.

Pros

  • No injection
  • Terminal acts as breadcrumb — browser stays in sync when you cd in shell
  • Natural for power users who cd frequently

Cons

  • Asymmetric — might feel surprising that one direction syncs but not the other
C

Detached by Default

Like A (fully independent), but you can push the current browser path to the linked terminal on demand with a key (e.g., Shift+Enter = "cd here in terminal"). The push is only sent when the terminal is known to be idle at a shell prompt (process group check).

Pros

  • Explicit = no surprises
  • Guards against injection when a process is running
  • Still ergonomic for the "navigate to a folder, then work there" flow

Cons

  • More complex to build (PTY idle detection is non-trivial)
  • Might feel less seamless than B

My recommendation: B (One-Way Observer) — fixes the injection bug completely, keeps the useful "shell cd = browser follows" behaviour, and requires the least implementation risk. Idle detection (needed for C) is a rabbit hole on macOS PTYs.
